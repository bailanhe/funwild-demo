# Part 3 · 跨平台产品策略 · Cross-platform Strategy

> 小程序 = 关系层 + 30 秒到 3 分钟 session。Website = 决策层 + 5 到 25 分钟 session。共享数据、分裂体验。

---

## 1. 核心命题 · 不能用 responsive 偷懒

许多团队把"做小程序 + Website"理解为"做一套 design system 适配两个 viewport"。这是 Funwild **必须避免的陷阱**。

理由：

### 1.1 同一用户在两端的**任务**不同
- 用户**在 Website**：陌生人状态，刚从小红书 / Google 跳过来。任务 = "我应该去哪里 + 我应该找谁 + 我要不要冒险"。
- 用户**在小程序**：熟客状态，从微信群 / push 进来。任务 = "这周末什么计划 + 我的徽章 + 有没有人约我"。

→ 如果用 responsive，**Website 的用户被强制看到小程序的动态流**（陌生人看不懂），**小程序的用户被强制看到 Website 的攻略大段文字**（不耐烦）。

### 1.2 同一用户在两端的**心理状态**不同
- 用户**在 Website**：浏览模式，多窗口对比，5-25 分钟 session。
- 用户**在小程序**：行动模式，单手拇指，30 秒-3 分钟 session。

→ 信息密度、CTA 数量、scroll 深度全都不同。强行统一会让两端都不舒服。

### 1.3 同一用户在两端的**进入场景**不同
- Website 入口：小红书外链、Google "Stubaier 中文攻略"、收藏夹回访。
- 小程序入口：微信对话框、N47 群消息、朋友圈链接、push 通知。

→ 入口决定了首屏要解决什么问题。Website 首页必须解决"我刚到，这是什么产品"；小程序首页必须解决"我熟了，现在该看什么"。

## 2. 双端心智边界 · 强约束矩阵

下面这张表是**两端设计的宪法**。任何子文档若违反，要么修正子文档，要么修正这张表（罕见）。

| 维度 | 小程序 | Website |
|---|---|---|
| **用户心理** | "我现在 / 这周末" | "我想知道 / 我准备去" |
| **session 长度** | 30 秒 - 3 分钟 | 5 - 25 分钟 |
| **进入场景** | 微信对话框、群消息、朋友圈链接、push | 小红书外链、Google 搜索、直接访问 |
| **设备 / 姿势** | 单手拇指、垂直滚动 | 双手键鼠 / 横向 + 垂直 |
| **核心交互** | 状态查看、社交动作（wave / 申请 / 报名）、打卡 | 信息消费、对比、深度阅读、客服咨询 |
| **数据写入主力** | 打卡、报名、拼车、徽章解锁、关注 | 注册（少量）、留资（咨询地接 / 客服） |
| **数据读取主力** | 我的动态、关注的人、消息、徽章 | 雪场攻略、教练对比、活动详情、SEO 关键词页 |
| **登录强度** | 微信无感登录（点开就登录） | 可登录可不登录（80% 内容免登录可看） |
| **网络效应** | 强（拼车、关注、群分享） | 弱（SEO 自然吸引） |
| **首屏目标** | 看见我的进行中 + 本周末雪友动态 | 看见这个产品是什么 + 直接进入感兴趣内容 |
| **CTA 数量** | 单屏 1-3 个 | 单屏 3-8 个 |
| **首屏 fold** | 414 × 600px（无标题栏区域） | 1280 × 720px（desktop） / 414 × 600（mobile web） |
| **信息密度** | 低（精选 + 提示） | 高（聚合 + 对比） |
| **Theme** | Sunset（默认）+ Pine（用户切换） | Pine（公开内容）+ Indigo（B2B 页面） |
| **字号 base** | 14px | 16px |

## 3. 双端共享的层 · Single Source of Truth

虽然 interaction 分裂，但底层必须共享，否则就是两个产品而不是一个平台。

### 3.1 共享数据层
- **用户**：profile、徽章、关注、订单、设置
- **内容**：雪场、教练、活动、地接、市集
- **行为**：打卡、报名、wave、评价、关注

### 3.2 共享品牌层
- 引用同一份 `brand_design/shared-tokens.jsx`
- 字体家族（Geist + Source Han Sans + Geist Mono）
- 徽章插画资产（142 SVG）
- Logo 与品牌色（虽然 theme 不同，logo 不变）

### 3.3 共享通知中心
- 用户在小程序里看到的"未读 3 条"和在 Website 登录后看到的"未读 3 条"是同一个数。
- 读了一边，另一边同步。

### 3.4 共享身份
- 一个用户在两端用同一个 Funwild ID
- 在 Website 注册 → 扫码进小程序自动登录
- 在小程序登录 → Website 扫码登录

## 4. 双端分裂的层 · 不应强制统一

### 4.1 首页布局
- 小程序首页 = 动态流（关注的人 + 我的进行中 + 推荐位）
- Website 首页 = Hero（品牌叙事）+ 攻略入口 + 教练 / 活动 / 地接概览 + 社区入口
- 不要试图把两个首页做成"同一个 layout 在不同 viewport"。

### 4.2 IA（导航结构）
- 小程序 IA：5 tab 底部导航
- Website IA：6 主导航 + 顶部搜索 + 登录区
- 详见 [part_05_information_architecture.md](./part_05_information_architecture.md)

### 4.3 搜索权重
- 小程序搜索：用户 / 动态 / 拼车 / 徽章优先
- Website 搜索：攻略 / SEO 关键词 / 雪场 / 教练优先
- 同一搜索词在两端排序不同。

### 4.4 Onboarding
- 小程序：微信无感登录 + 2 步偏好 + 解锁徽章 < 30 秒
- Website：渐进式，先看内容再注册。"注册"是次要 CTA，"扫码进小程序"是主要 CTA。

### 4.5 视觉 theme
- 小程序：Sunset（默认）+ Pine（用户切换）
- Website：Pine（公开内容）+ Indigo（B2B）

## 5. 跨端"接力棒" · 5 个关键互通点

用户旅程不在单端结束。每个接力点都要做得无 friction。

### 5.1 接力点 A · Website 攻略 → 小程序收藏夹
**场景**：2B 国内游客在 Website 看 Stubaier 攻略，决定"我以后还要回来看"。
**机制**：
- Website 攻略页右侧浮"⊕ 加入收藏 → 扫码同步到小程序"
- 扫码后小程序"我的收藏"自动加入这条
- 用户下次在小程序"我的收藏"里看到的是同一条 + 增加"距离上次浏览 X 天"
**实现**：扫码 deep link 带 attraction_id，落 device id 做匿名映射

### 5.2 接力点 B · Website 教练 → 小程序联系
**场景**：2A 高消费家庭在 Website 比较 3 个教练，决定联系其中 1 个。
**机制**：
- Website 教练页 CTA = "扫码联系（在小程序）"
- 扫码后小程序教练详情页直接打开 + "发起 wave"按钮高亮
**实现**：deep link 带 coach_id

### 5.3 接力点 C · 小程序分享海报 → Website 落地页
**场景**：1B 周末玩家打卡后生成海报，发到朋友圈。朋友圈外人点击海报二维码。
**机制**：
- 海报二维码指向 Website 短链（如 `funwild.com/u/abc123/checkin/xyz789`）
- Website 落地页显示：用户头像 + 打卡详情 + "扫码进小程序看更多 Stubaier 攻略"
**实现**：Website 落地页是 SSR 静态页，SEO indexable

### 5.4 接力点 D · 小程序"打开网页版"按钮
**场景**：1A Hardcore 在小程序看 Stubaier，想要深度对比 / 横屏看雪道图。
**机制**：
- 小程序雪场详情页右上角"在网页版打开"按钮
- 点击生成二维码，用户用桌面浏览器扫码 → Website 雪场页打开
**实现**：可选功能，Year 1 用得不多，但 Hardcore 用户会感激

### 5.5 接力点 E · Website 注册 → 小程序自动登录
**场景**：2B 用户在 Website 注册了，第一次扫码进小程序。
**机制**：
- Website 注册后落 device id cookie + 邮箱/微信关联
- 用户在同一台设备扫码进小程序，小程序识别 device id → 自动登录
**实现**：跨域 cookie / Storage，复杂但用户感受极好

## 6. 双端协同的内容策略

### 6.1 同一内容在两端的不同形态

以"Stubaier 雪场攻略"为例：

| 形态 | Website | 小程序 |
|---|---|---|
| **首屏** | Hero 大图 + 标题 + 元数据（车程 / 海拔 / 雪季） | 雪场名 + 打卡数 + 4 快速行动按钮 |
| **核心内容** | 1500 字详细攻略 + 雪道图 + 高清照片 | ❗ 特别提醒 + 新手一日动线 + 教练联动 |
| **CTA** | 8 个 CTA（扫码加入收藏 / 找教练 / 看活动 / PDF / 分享 / 客服 / 入驻服务商 / 报名活动） | 4 个 CTA（打卡 / 发拼车 / 找教练 / 找地接） |
| **互动** | 评论区（V1.2）+ 相关攻略推荐 | 这周末谁去 + 我的徽章进度 |
| **页面长度** | 5-8 屏 scroll | 3-4 屏 scroll |

### 6.2 内容产能复用

雪场攻略写一次，可输出到 6 个地方：
1. Website 雪场详情页（核心）
2. 小程序雪场详情页（精简版）
3. PDF 离线攻略（发到微信）
4. 小红书品牌号笔记（4 类内容之一）
5. 微信公众号文章
6. 抖音脚本（V1.1）

→ 内容团队（欧根 + 团队众包）的 ROI 由这种复用最大化。

## 7. 双端开发的工程约束

### 7.1 Year 1 工程优先级
| 优先级 | 双端任务 |
|---|---|
| **P0** | 小程序前后端（杜蕊珈 + 陆洲） |
| **P0** | Website 18 雪场静态 SEO 落地页（可用 Notion / Webflow 兜底） |
| **P1** | Website 教练 profile 公开页（独立 URL） |
| **P1** | 双端用户登录互通 |
| **P2** | Website 完整 IA + 客服咨询页 |
| **P2** | Website 活动 / 地接 / 社区页 |
| **P3** | Website 后台（V1.1 教练入驻自助） |

### 7.2 工程不应该重复造的轮子
- 用户系统 / 认证：双端共享一套 backend
- 内容 CMS：双端读同一套数据库
- 通知系统：双端 push 同一套消息

### 7.3 工程必须分开做的部分
- 小程序：微信原生（uni-app / Taro / 原生）
- Website：React / Next.js（支持 SSR + SEO）
- 共享：BFF API 层 + 同一份 design token

## 8. 案例 · 同一用户的双端 timeline

> Persona: 2B 年轻自由行 · 25 岁 · 上海 · 计划 12 月去欧洲滑雪 7 天

### Week -6（决策初期）
**Day 1**（小红书发现）：在小红书刷到"欧洲 7 天滑雪攻略 #趣野Funwild"笔记。点击外链。

**Day 1 (continued)**（Website 第一次访问）：跳转到 `funwild.com/resort/austria/stubaier-gletscher/`。Hero 大图 + ❗特别提醒。停留 8 分钟读完。
- 看到底部 "扫码进小程序找教练" → 不想注册，关闭

**Day 3**（Website 第二次访问）：Google "Stubaier 中文攻略"，又到 Funwild 同一页。这次往下看完全部 + 看到 "适合 7 天行程的推荐路线"
- 加入收藏（扫码生成短链）

### Week -4（决策中期）
**Day 8**（Website 教练对比）：在 Funwild Website 看了 3 个 Stubaier 教练页面 + 比较了语言 / 价格 / 评价
- 决定联系张磊教练
- 扫码进小程序"教练 张磊"页 → wave 给张磊

**Day 8 (continued)**（小程序第一次访问）：扫码自动跳到张磊教练页 → 注册 + onboarding < 30 秒 → 自动 wave
- 5 分钟后张磊回 wave + 自动打开微信对话框
- 微信里张磊问"你想要什么样的课？"

### Week -3（行前准备）
**Day 15**（小程序 daily 打开）：客服微信告知"行前 PDF 已发"
- 小程序"我的 → 我的收藏 → Stubaier 攻略"再次浏览
- 添加 Funwild 服务号 → 接受订阅消息

### Week 0（行中）
**Day 30**（行中 day 1）：到达 Stubaier 第一天
- 小程序首页 hero "📍 你在 Stubaier 5km 内 → 打卡？"
- 打卡 → 解锁"欧洲首次打卡"徽章 → 海报自动生成
- 发到朋友圈

**Day 30 (continued)**（朋友圈传播）：朋友圈一个朋友点击海报二维码
- Website 落地页打开：用户头像 + Stubaier 打卡 + "扫码进小程序看更多"
- 朋友扫码进小程序 → 新用户注册

### Week +1（行后）
**Day 37**（行后第 7 天）：小程序 push "评价你的教练张磊，可解锁'攻略救了我'徽章"
- 写评价 → 解锁徽章
- "把这次旅行写成攻略可得 3 个徽章" → 用模板写攻略 → 发到小红书

**Day 40**：在 Website `funwild.com/u/zhang-xiaomei/` 看到自己的公开主页（V1.1 上线后）
- 看到完整徽章墙 + 评价 + 攻略链接
- 转发给朋友"看我的 Funwild 主页"

### 总结
- **跨平台触点**：小红书 → Website × 3 次 → 小程序 × N 次 → Website 落地页（被朋友访问） → Website 公开主页
- **共享数据**：收藏、徽章、评价、关注、订单
- **分裂体验**：Website 是深度内容 + 决策，小程序是即时行动 + 社交

→ 任何"用 responsive 偷懒"的方案都做不出上面这个 timeline。

## 9. 失败案例 · 常见双端设计错误

下面是其他产品 / 团队常犯的错误，Funwild 必须避免。

| 错误 | 后果 | Funwild 对策 |
|---|---|---|
| Website = 小程序的 H5 镜像 | Website 0 SEO，搜索引擎完全找不到 | Website 必须 SSR + indexable 攻略页 |
| 小程序 = Website 的 mobile responsive | 小程序流畅性 + 微信原生体验失败 | 小程序用 uni-app / Taro / 原生开发 |
| 两端都要用户先登录 | 80% 陌生人在 Website 注册门槛流失 | Website 80% 内容免登录 |
| 两端都把"动态流"塞进首页 | Website 陌生人看不懂 | Website 首页 = 内容入口，不是动态 |
| 两端都做"全功能首页" | 用户在两端都迷茫 | 小程序 = 关系流，Website = 内容流 |
| Logo / 颜色 / 字体两端不一致 | 用户怀疑两端不是同一产品 | 共享 brand_design tokens + Logo |

## 10. 总结 · 双端最重要的 3 件事

1. **共享数据 + 分裂体验**——一个用户、一份数据、两种心智。
2. **跨端接力棒做无 friction**——扫码 / 短链 / device id 全部要打通。
3. **不要用 responsive 偷懒**——投入两套前端是值得的。
